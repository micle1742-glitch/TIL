# chap03 - 연관관계 매핑 복습

## 0. 오늘의 큰 그림
- 테이블: tbl_menu.category_code(FK) → tbl_category.category_code
- 객체: Menu가 `int categoryCode` 대신 **Category 객체**를 참조 (chap00 패러다임 불일치 해결)
- section01 N:1 단방향 (Menu → Category)
- section02 1:N 단방향 (Category → List<Menu>)
- section03 양방향 (Menu ↔ Category) + 연관관계의 주인, mappedBy

| | 어디에 매핑 | 어노테이션 | FK 관리 |
|---|---|---|---|
| N:1 단방향 | Menu.category | `@ManyToOne` + `@JoinColumn` | Menu |
| 1:N 단방향 | Category.menuList | `@OneToMany` + `@JoinColumn` | (여기선 insertable/updatable = false로 조회만) |
| 양방향 | Menu.category + Category.menuList | `@ManyToOne @JoinColumn` + `@OneToMany(mappedBy)` | Menu (주인) |

## 2) N:1 단방향 - @ManyToOne

    @Entity(name = "Section01Menu")
    @Table(name = "tbl_menu")
    public class Menu {
        @Id
        @Column(name = "menu_code")
        private int menuCode;                   // @GeneratedValue 없음 → 직접 9001 넣음

        @ManyToOne(fetch = FetchType.LAZY)
        @JoinColumn(name = "category_code", nullable = false)   // tbl_menu의 FK 컬럼
        private Category category;
    }

    // 등록: 카테고리 엔티티를 먼저 찾아서 연결
    @Transactional
    public Menu registMenu(MenuDTO menuInfo) {
        Category category = manyToOneRepository.findCategory(menuInfo.getCategoryCode());
        if (category == null) throw new IllegalArgumentException("존재하지 않는 카테고리입니다");
        Menu menu = new Menu(menuInfo.getMenuCode(), ..., category, ...);
        return manyToOneRepository.save(menu);   // persist
    }

    // 조회: 메뉴에서 카테고리로 탐색
    Menu foundMenu = manyToOneService.findMenu(10);
    foundMenu.getCategory().getCategoryName();   // LAZY → 이때 카테고리 SELECT

- `@JoinColumn(name)`: **내 테이블(tbl_menu)의 FK 컬럼 이름**
- DTO는 categoryCode(숫자)로 받고, Service에서 Category 엔티티로 바꿔서 연결
- PK를 직접 넣는 방식이라 persist 때가 아니라 flush/commit 때 INSERT (테스트에서 `flush()`)

## 3) 1:N 단방향 - @OneToMany

    @Entity(name = "Section02Category")
    @Table(name = "tbl_category")
    public class Category {
        @Id
        @Column(name = "category_code")
        private int categoryCode;

        @OneToMany(fetch = FetchType.EAGER)
        @JoinColumn(name = "category_code", insertable = false, updatable = false)
        private List<Menu> menuList;
    }
    // section02의 Menu는 연관관계 없이 int categoryCode만 가짐

    Category category = oneToManyService.findCategory(4);
    category.getMenuList();      // 4번 카테고리의 메뉴들

- 여기서 `@JoinColumn(name = "category_code")`는 Category 테이블이 아니라 **상대(tbl_menu)의 FK 컬럼**
- `insertable = false, updatable = false`: Menu 쪽 categoryCode 필드가 같은 컬럼을 이미 관리 → Category에서는 FK를 넣거나 바꾸지 않고 **조회만**
- 강사님 코드 주석: @OneToMany 기본은 LAZY, @ManyToOne 기본은 EAGER → 여기선 일부러 EAGER로 지정

## 4) 양방향 - 연관관계의 주인과 mappedBy

    // Menu: 연관관계의 주인 (FK가 있는 쪽)
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "category_code", nullable = false)
    private Category category;

    // Category: 주인이 아닌 쪽 (읽기 전용)
    // mappedBy에는 DB 컬럼명이 아니라 반대편 Menu의 연관관계 필드명 category를 적는다
    @OneToMany(mappedBy = "category")
    private List<Menu> menuList = new ArrayList<>();

    // 연관관계 편의 메소드
    public void addMenu(Menu menu) {
        menuList.add(menu);          // 카테고리 → 메뉴
        menu.setCategory(this);      // 메뉴 → 카테고리 (실제 FK에 반영되는 쪽)
    }

    // 테스트
    Category foundCategory = biDirectionService.findCategory(4);
    assertSame(foundCategory, foundCategory.getMenuList().get(0).getCategory());   // 같은 객체

- **연관관계의 주인** = FK를 가진 테이블(tbl_menu)과 매핑된 쪽 = `@ManyToOne`이 있는 Menu
- 주인만 FK 값을 등록/수정할 수 있음. `category.getMenuList().add(menu)`만 하면 DB엔 반영 안 됨
- 편의 메소드로 **양쪽 객체를 같이** 맞춰야 메모리상 객체 상태도 일치
- assertSame: 같은 영속성 컨텍스트라 메뉴가 가리키는 카테고리 = 조회한 그 카테고리 객체

## 5) toString 무한 루프 주의

    // Menu.toString()   → ..., category=" + category        (Category 출력)
    // Category.toString() → menuList는 빼고 출력

- 양방향에서 둘 다 상대를 출력하면 Menu → Category → Menu → ... 무한 호출 (StackOverflowError)
- 그래서 Category의 toString에는 menuList를 넣지 않음

## 헷갈리는 부분

**1. @OneToMany(mappedBy) vs @JoinColumn**
- `@JoinColumn(name = "category_code")`: "이 FK 컬럼으로 연결한다" → FK를 관리하는 쪽에 씀
- `mappedBy = "category"`: "FK는 상대 엔티티의 category **필드**가 관리한다, 나는 읽기만" → 주인이 아닌 쪽에 씀
- mappedBy에는 컬럼 이름(category_code)이 아니라 **필드 이름**(category)
- 양방향에서 둘 다 @JoinColumn을 쓰면 FK를 두 군데서 관리하게 됨 → 한쪽은 mappedBy

**2. 연관관계의 주인은 누구?**
- FK가 있는 쪽 = N(다) 쪽 = @ManyToOne 쪽 = Menu
- "더 중요한 쪽"이 아니라 "FK를 가진 쪽"

**3. 기본 fetch 전략**
- `@ManyToOne` 기본 EAGER, `@OneToMany` 기본 LAZY
- 실무에선 @ManyToOne도 LAZY로 지정 (EAGER는 필요 없을 때도 조인/추가 쿼리)
- LAZY는 처음에 가짜 객체(프록시)를 넣어 두고 실제로 값을 꺼낼 때 SELECT

**4. LAZY 조회가 테스트에서 되는 이유**
- Service는 readOnly 트랜잭션이 끝났지만, 테스트 클래스의 @Transactional이 바깥에서 트랜잭션을 유지 → 영속성 컨텍스트가 살아 있어서 LAZY 로딩 가능
- chap04처럼 트랜잭션 밖(Controller)에서 꺼내면 LazyInitializationException

**5. 1:N 단방향의 @JoinColumn은 상대 테이블 컬럼**
- @ManyToOne의 @JoinColumn: 내 테이블 FK / @OneToMany의 @JoinColumn: 상대(N쪽) 테이블 FK

---

## 암기할 것
- `@ManyToOne(fetch = FetchType.LAZY)` + `@JoinColumn(name = "FK 컬럼")`
- `@OneToMany(mappedBy = "상대 엔티티의 필드명")`
- 주인 = FK 있는 쪽(@ManyToOne), 주인만 FK 변경 가능
- 기본 fetch: ManyToOne = EAGER, OneToMany = LAZY
- 연관관계 편의 메소드: 양쪽 객체를 한 번에 세팅
- 양방향 toString은 한쪽에서 끊기

---

## 전체 흐름 정리
- 객체는 FK 숫자 대신 연관 객체를 필드로 가짐
- N:1은 Menu에 @ManyToOne + @JoinColumn, 1:N은 Category에 @OneToMany
- 양방향이면 FK를 가진 Menu가 주인, Category는 mappedBy로 읽기 전용
- 저장할 때는 연관 엔티티를 먼저 조회해서 연결, 편의 메소드로 양쪽을 같이 맞춤
- LAZY 연관 객체는 영속성 컨텍스트가 살아 있는 동안 꺼내야 함 → chap04 Service 안 DTO 변환, chap05 JOIN FETCH로 이어짐
