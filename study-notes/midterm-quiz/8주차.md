# 정답

| 번호 | 정답 | 해설 |
|---|---|---|
| 1 | ORM(Object-Relational Mapping) | JPA는 Java의 ORM 표준이다. |
| 2 | ① JPA | Hibernate는 JPA를 실제로 구현한 구현체이다. |
| 3 | 패러다임 불일치 | 상속, 연관관계, 객체 그래프 탐색에서 차이가 생긴다. |
| 4 | SQL 의존 | 객체에 무엇이 채워질지를 SQL이 결정해서, 객체만 보고는 믿고 쓸 수 없다. |
| 5 | false | 조회할 때마다 새 객체를 만들기 때문이다. JPA는 같은 영속성 컨텍스트 안에서 같은 객체를 돌려준다. |
| 6 | ② EntityManagerFactory | EntityManager는 작업마다 새로 만들고 스레드끼리 공유하지 않는다. |
| 7 | createEntityManagerFactory | EntityManager는 `factory.createEntityManager()`로 만든다. |
| 8 | 영속성 컨텍스트 | EntityManager마다 자기 영속성 컨텍스트를 가진다. |
| 9 | true | 두 번째는 1차 캐시에서 꺼내므로 SELECT는 1번만 나가고 같은 객체가 반환된다. |
| 10 | 변경 감지(dirty checking) | 그래서 JPA에는 update 메소드가 따로 없다. |
| 11 | ② flush() | flush 후에도 rollback하면 되돌릴 수 있다. commit은 flush + 확정이다. |
| 12 | ① 비영속 | PK와 값이 DB 행과 같아도 JPA가 관리하지 않으면 비영속이다. |
| 13 | ③ 준영속 | 식별자는 있지만 관리되지 않아 변경 감지가 동작하지 않는다. |
| 14 | 실행 안 됨 | detach로 준영속이 되어 변경 감지 대상이 아니다. |
| 15 | false true | merge는 넘긴 객체가 아니라 값을 복사한 영속 객체를 반환한다. 이후에는 반환값을 써야 한다. |
| 16 | GenerationType.IDENTITY | INSERT를 해야 PK를 알 수 있어서 persist 시점에 바로 INSERT가 실행된다. |
| 17 | ② @Enumerated(EnumType.STRING) | 기본값 ORDINAL은 순서 번호(0, 1)로 저장해서 enum 순서를 바꾸면 의미가 바뀐다. |
| 18 | 기본 생성자, protected | 예: `protected Member() {}` — public이면 아무 데서나 빈 객체를 만들 수 있다. |
| 19 | ④ create | 기존 데이터가 사라지므로 실제 데이터가 있는 DB에는 쓰지 않는다. chap03부터는 none을 사용했다. |
| 20 | @Embeddable | 그 값 객체를 쓰는 엔티티 필드에는 @Embedded를 붙인다. |
| 21 | 38700 | 43000 - 4300 = 38700. 할인율이 0~1 밖이면 생성자에서 IllegalArgumentException이 발생한다. |
| 22 | @PersistenceContext | Spring을 쓰면 트랜잭션 begin/commit도 @Transactional이 대신한다. |
| 23 | category_code | @ManyToOne의 @JoinColumn name은 내 테이블(tbl_menu)의 FK 컬럼 이름이다. |
| 24 | ② Menu (@ManyToOne 쪽) | 주인은 FK를 가진 테이블(tbl_menu)과 매핑된 쪽이다. |
| 25 | ② category | mappedBy에는 DB 컬럼명이 아니라 반대편 엔티티의 연관관계 필드명을 쓴다. |
| 26 | ② @OneToMany(mappedBy = "category") | @JoinColumn은 FK를 관리하는 주인 쪽에 쓴다. |
| 27 | ① @ManyToOne = EAGER, @OneToMany = LAZY | 수업 코드는 @ManyToOne에 fetch = FetchType.LAZY를 직접 지정했다. |
| 28 | 연관관계 편의 메소드 | 주인 쪽(menu.setCategory)만 FK에 반영되지만, 메모리의 양쪽 객체도 맞춰 두기 위해 쓴다. |
| 29 | StackOverflowError | Menu → Category → Menu ... 무한 호출이 된다. 그래서 Category의 toString에서 menuList를 뺐다. |
| 30 | Category 쪽에서는 FK 값을 넣거나 바꾸지 않고 조회만 한다 | 같은 category_code 컬럼을 Menu의 categoryCode 필드가 이미 관리한다. |
| 31 | Integer | 두 번째 제네릭은 엔티티 @Id 필드의 타입이고, 제네릭에는 기본형을 쓸 수 없다. |
| 32 | Optional<Menu> | 없을 수도 있어서 Optional이다. `.orElseThrow(() -> new ResourceNotFoundException(...))`로 꺼낸다. |
| 33 | UPDATE | findById로 꺼낸 영속 엔티티를 바꿨기 때문에 커밋 직전 flush에서 변경 감지가 UPDATE를 만든다. |
| 34 | ② @Transactional(readOnly = true) | 데이터를 바꾸는 등록·수정·삭제에는 그냥 @Transactional을 쓴다. |
| 35 | 반영 안 됨 | readOnly에서는 flush를 하지 않아 UPDATE가 나가지 않는다. 에러도 나지 않아서 찾기 힘든 버그가 된다. |
| 36 | LazyInitializationException | 영속성 컨텍스트가 닫혀 LAZY 로딩을 못 한다. 그래서 Service 안에서 DTO로 변환한다. |
| 37 | ResourceNotFoundException | RuntimeException을 상속하고, Handler는 `new ErrorResponse(exception.getMessage())`를 본문으로 보낸다. |
| 38 | noContent | 본문이 없으니 반환 타입은 ResponseEntity<Void>이다. |
| 39 | menuPrice >= 20000 | GreaterThanEqual은 >=, 결과는 OrderByMenuPriceDesc로 가격 내림차순이다. |
| 40 | ① 쿼리 메소드 | 이름 속 MenuName은 컬럼이 아니라 엔티티 필드 menuName이다. |
| 41 | ② JPQL | 실행할 때 Hibernate가 매핑 정보를 보고 실제 SQL로 바꾼다. |
| 42 | Menu | JPQL의 FROM에는 테이블 이름이 아니라 엔티티 이름을 쓴다. |
| 43 | @Param | `:keyword`와 @Param("keyword")의 이름이 같아야 한다. |
| 44 | @PageableDefault | 요청 예: `?page=0&size=5&sort=menuCode,asc` — page는 0부터 시작한다. |
| 45 | ① page.map(this::toResponse) | stream().map().toList()는 결과가 List라 페이지 정보가 사라진다. |
| 46 | N+1 문제 | 목록 1번 + 연관 객체 조회 N번이 실행된다. |
| 47 | JOIN FETCH | 일반 JOIN은 조인만 하고 category는 여전히 LAZY로 남는다. |
